# Phase 05.1: Streamlit Video Platform UI - Research

**Researched:** 2026-02-20
**Domain:** Streamlit export target UX + review-state persistence + render wiring integrity
**Confidence:** HIGH

## Summary

Phase 05 already added backend support for `spotify_video`, `apple_video`, and `apple_hls`, but Streamlit export UX is still exposing only legacy platform options (`youtube`, `spotify`, `apple`, and short-form platforms). This creates a truth gap: operators cannot explicitly select the video podcast targets already supported by render.

The implementation should remain schema-driven and backward-compatible. `review/review_state.json` is already the canonical contract (`ReviewDecisions.export_platforms`), and render already consumes it (`RenderStage.run`). The safe plan is to update Streamlit target definitions, preserve existing defaults (`youtube,spotify`), and add explicit guardrails for unknown keys and `apple_hls` workflow boundaries.

As of 2026-02-20, Streamlit docs and release notes support a cleaner multi-select interaction pattern; Pydantic v2 default extra-field handling supports backward compatibility for legacy/new review state fields; Apple and Spotify docs still confirm that pipeline scope is artifact generation, not direct upload automation.

**Primary recommendation:** Use a canonical platform registry shared by Streamlit export panel and validation helpers, then persist only validated keys to `review_state.json` while preserving defaults and legacy job behavior.

## Architecture Patterns

### Recommended Project Structure

```text
src/podcast_pipeline/
├── ui/app.py                  # Canonical export option registry + export panel rendering
├── stages/review.py           # ReviewDecisions defaults and persistence contract
├── stages/render.py           # Render-time target consumption + unsupported-key guardrails
└── cli.py                     # Approve command platform argument semantics
tests/
├── test_ui_app.py             # UI option visibility + persistence + approve/export path tests
├── test_integration.py        # review_state -> render wiring tests
└── test_render.py             # platform-key handling and failure contract tests
```

### Pattern 1: Canonical Target Registry (Single Source of Truth)
**What:** Define one mapping for export target keys, display labels, type (audio/video/package), and workflow guidance.
**When to use:** Any UI rendering, key validation, docs generation, or CLI alignment check.
**Example:**
```python
EXPORT_TARGETS = [
    {"key": "spotify", "label": "Spotify (Audio)", "group": "audio"},
    {"key": "apple", "label": "Apple Podcasts (Audio)", "group": "audio"},
    {"key": "spotify_video", "label": "Spotify Video (MP4)", "group": "video"},
    {"key": "apple_video", "label": "Apple Video (MP4)", "group": "video"},
    {
        "key": "apple_hls",
        "label": "Apple HLS (Package)",
        "group": "package",
        "note": "Creates artifacts for provider-mediated publishing; no direct upload automation.",
    },
]
```

### Pattern 2: Backward-Compatible Review State Read/Write
**What:** Load review state through `ReviewDecisions.model_validate_json`, then normalize/export valid keys only.
**When to use:** Export tab load/save and approve/export actions.
**Example:**
```python
decisions = ReviewDecisions.model_validate_json(review_path.read_text())
selected = [k for k in decisions.export_platforms if k in allowed_keys]
if not selected:
    selected = ["youtube", "spotify"]
```

### Pattern 3: Fail Loudly for Unsupported Keys at Render Boundary
**What:** Keep UI safe, but also preserve render-stage defensive behavior for malformed/manual states.
**When to use:** Before platform loop in `RenderStage.run` and per-platform result reporting.
**Example:**
```python
spec = self._get_platform_spec(platform)
if spec is None:
    platform_results[platform] = {"status": "failed", "error": f"{platform}: Unsupported platform"}
```

### Anti-Patterns to Avoid
- **UI-only truth:** Adding new targets in README/config but not Streamlit export panel.
- **Silent key dropping without feedback:** Losing user-selected keys with no warning makes operations non-deterministic.
- **Over-promising `apple_hls`:** Presenting it as direct publish instead of artifact packaging for provider-mediated workflow.
- **Divergent defaults across surfaces:** Streamlit and CLI should retain aligned default intent (`youtube,spotify`) unless explicitly changed.

## Don't Hand-Roll

Problems that look simple but have existing solutions:

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| JSON schema migration layer for review state | Custom migration scripts for every key addition | Pydantic v2 model defaults + extra ignore behavior | Handles missing/new fields with less risk and fewer moving parts |
| Complex widget state orchestration for each checkbox | Manual per-key synchronization logic | Streamlit keyed widgets or `st.multiselect` + deterministic normalization | Reduces stale widget metadata and rerun inconsistencies |
| Custom HLS publication automation | In-repo direct Apple publishing integration | Existing `apple_hls` artifact generation + operator guidance | Apple workflow is provider-mediated via Apple Podcasts Connect API keys |

**Key insight:** The hard part is preserving cross-surface truth (UI/CLI/render/docs), not building new infrastructure.

## Common Pitfalls

### Pitfall 1: UI options lag backend capabilities
**What goes wrong:** Render supports targets that operators cannot select.
**Why it happens:** Platform list hardcoded in UI diverges from config/review/render contracts.
**How to avoid:** Centralize target registry and assert expected keys in tests.
**Warning signs:** `config.yaml`/render include keys not present in export panel.

### Pitfall 2: Legacy review states break after key expansion
**What goes wrong:** Old jobs fail validation or export empty target sets.
**Why it happens:** Missing normalization/fallback when loading persisted decisions.
**How to avoid:** Preserve defaults and normalize unknown keys defensively.
**Warning signs:** Export button persists `[]` or raises validation errors on old jobs.

### Pitfall 3: `apple_hls` UX implies direct publishing
**What goes wrong:** Operators assume pipeline pushes to Apple directly.
**Why it happens:** Insufficient help text and docs boundaries.
**How to avoid:** Label as "Package" and include provider-mediated warning in UI/README.
**Warning signs:** Runbooks mention direct upload from this pipeline.

### Pitfall 4: CLI/UI semantics drift
**What goes wrong:** `approve --platforms` behavior differs from Streamlit selection expectations.
**Why it happens:** Independent parsing/normalization paths.
**How to avoid:** Reuse one canonical set of accepted keys and defaults.
**Warning signs:** Same job approved via CLI vs UI produces different targets unexpectedly.

## Open Questions

1. **Should Streamlit export UI retain checkbox grid or switch to `st.multiselect` now?**
   - What we know: `st.multiselect` is stable and simpler for persistence.
   - What's unclear: UX preference for glanceable grouped toggles.
   - Recommendation: Keep grouped checkboxes if preferred, but derive from one registry and add tests; otherwise migrate to `multiselect`.

2. **Should CLI accept repeated `--platform` in addition to comma-separated string?**
   - What we know: Typer supports repeated list options natively.
   - What's unclear: Whether changing CLI UX now risks breaking operator scripts.
   - Recommendation: Keep current comma-separated input in 05.1; add optional repeated form in a follow-up compatibility enhancement.

3. **Should unknown persisted keys be retained (opaque) or dropped (strict)?**
   - What we know: Strict drop improves safety, but can hide data if key was temporarily unsupported.
   - What's unclear: Team preference for forward compatibility vs strictness.
   - Recommendation: Drop unknown keys for execution, but log warning and surface UI notice.
